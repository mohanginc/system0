# system0 송장 정정과 채팅 선택 및 SKU 적용 작업 계획

작성일: 2026년 11월 13일  
수정일: 2026년 11월 14일 — 송장·채팅과 SKU 로컬 구현 결과 반영
상태: 송장·채팅·SKU·상품 관리·공통 메뉴·AI 호출 비용을 구현했다. 자동 테스트 336개와 실제 로컬 화면 검증을 완료했다. 커밋·운영 반영 결과와 보존 검사는 배포 기록으로 관리한다.

송장 정정 시 생기는 충돌과 다운로드 차단을 먼저 해결한다. 채팅에서는 일괄 정정과 소수 주문의 송장 선택을 지원하고, 웹과 동일한 결과를 저장한다. SKU 적용은 별도 단계로 진행하여 상품명 정리 화면에 바코드를 표시하고 출고보드를 바코드 기준으로 묶는다.

## 1 현재 발생한 송장 문제

| 문제 | 관찰한 현상과 확인 수준 |
| --- | --- |
| 복수 송장의 자동 선택 | 오늘 디스코드 작업은 송장이 두 개 있는 주문에도 선택을 요청하지 않고 앞 번호로 엑셀을 생성했다. 사용자 제공 파일과 화면을 기준으로 보고된 현상이다. |
| 정정 업로드에 과거 번호가 섞임 | 격리된 메모리 DB에서 재현했다. 1차·2차 번호를 올린 뒤 2차 번호만 재업로드해도 이전 번호가 내부 이력에 합쳐지고, 대표 번호는 1차로 남았다. |
| 수취 정보 충돌 오탐 가능성 | 코드에서 과거 송장의 수취 정보가 JSON 저장에서 빠지고, 현재 업로드 원본만으로는 이를 복원하지 못하는 경로를 확인했다. 빈 정보와 현재 수취 정보를 비교해 `courier_conflict`를 만들 수 있다. 오늘 운영의 모든 충돌이 이 원인인지는 원본 대조가 더 필요하다. |
| 검토 저장 후 다운로드 불가 | 화면에는 새 번호 하나만 보이지만 내부의 충돌은 남아 있다. 경고 확인 저장은 적용 송장 확정과 다르므로 차단이 해제되지 않는다. |
| 이전 엑셀과 정정 결과의 혼동 | 디스코드의 기존 메시지에서 ‘엑셀 받기’를 누르면 보관된 이전 파일을 반환한다. 정정 결과로 만든 새 파일과 명확하게 구분해야 한다. |

위 내용은 11월 13일 진단 기준이다. 11월 14일에는 백업 API로 받은 격리 복사본과 업로드 원본으로 대조·검증했으며, 결과는 10절에 기록한다. 운영 데이터 수정이나 송장 교체는 실행하지 않았다.

## 2 송장 처리 원칙

- 네이버 최종 파일의 상품주문을 이번 처리 대상으로 삼는다. 날짜가 다른 저장 주문도 같은 기준으로 연결한다.
- 일반 재업로드에서 빠진 번호를 자동으로 취소하거나 폐기하지 않는다. 직원이 교체를 명시한 출고 범위에서만 이전 번호를 교체 이력으로 전환한다.
- 직원 선택이나 확실한 재발급 근거 없이 여러 번호가 남으면 엑셀 자동 생성을 멈춘다. 출력 순서·큰 번호·LLM 추측만으로 하나를 고르지 않는다.
- 실제 분할 배송은 전체 실물 송장을 유효하게 보존하고 네이버에 등록할 대표 번호를 따로 정한다. 사고로 인한 교체와 구분한다.
- 실제 수취 정보 차이, 주문 연결 불명확, 네이버에 다른 번호가 등록된 상태는 교체 확인이나 경고 체크만으로 우회하지 않는다.
- 같은 출고에 연결된 여러 상품주문은 함께 처리한다. 화면 행 수와 네이버 상품주문 수가 다를 수 있으므로 변경 요약에 두 수를 구분한다.
- 과거 송장, 업로드 원본, 검토 이력과 생성 엑셀을 보존한다. 정정 결과는 새 처리 내역과 새 파일로 남긴다.

## 3 직원이 사용할 송장 처리 흐름

### 3.1 오늘처럼 여러 주문을 일괄 정정하는 경우

1. 직원이 재출력한 번호만 남긴 로젠 파일과 최종 네이버 파일을 첨부한다. ‘기존 송장을 이 파일로 교체해줘’라고 요청한다.
2. 봇은 기존 번호와 새 파일의 차이를 계산하고, 교체할 출고 수·상품주문 수·확인이 필요한 항목 수를 보여준다.
3. 직원은 **이번 파일의 송장으로 교체**를 한 번 누른다. 정상적으로 연결되는 각 출고를 개별 체크할 필요는 없다.
4. 시스템은 확인된 범위의 새 번호를 적용하고 이전 번호는 교체 이력으로 보관한다. 웹 화면에도 같은 결과를 표시한다.
5. 미해결 항목이 없으면 새 엑셀을 생성한다. 일부 주문이 누락되었거나 번호가 여럿이면 그 항목만 추가로 물어보고 생성 전 해결한다.

확인 버튼은 명확하게 연결된 대상에만 적용한다. 새 파일에 없는 다른 주문이나 다른 날짜의 출고까지 일괄 변경하지 않는다. 단순히 파일을 다시 올렸다는 이유만으로 교체를 확정하지 않는다.

### 3.2 평소 한두 주문에 송장이 여러 개 있는 경우

1. 정상 매칭 주문은 준비해 두고, 선택이 필요한 주문만 봇 메시지에 표시한다.
2. 수취인, 주문 식별 정보, 후보 번호를 보여주고 선택 메뉴로 적용할 번호를 받는다. 출력 시각·차수는 원본에 실제 값이 있을 때 함께 표시한다.
3. 기존 번호 교체인지 실제 분할 배송인지 구분한다. 분할 배송에서는 나머지 실물 송장을 폐기하지 않고 대표 번호만 선택한다.
4. **선택 완료 · 엑셀 만들기**를 누르면 선택 결과를 저장하고 전체 처리 대상의 새 파일을 만든다. 보류할 주문은 제외 사실과 건수를 보여준다.

예시 문구는 ‘18건 중 2건은 송장 선택이 필요합니다’로 충분하다. 선택하지 않은 주문을 앞 번호로 자동 확정하지 않는다. 후보가 많거나 연결 근거가 불명확한 경우에는 해당 작업의 웹 검토 화면으로 연결한다.

### 3.3 웹과 채팅에서 이어서 작업하는 경우

- 송장 선택·교체·보류·파일 생성은 공통 업무 API를 사용한다. 채팅 전용 매칭 로직을 만들지 않는다.
- 채팅에서 선택한 번호는 웹에서 선택된 상태로 보이고, 웹에서 저장한 결과도 봇이 이어서 읽는다.
- ‘경고 확인’과 ‘적용 송장 선택’을 구분한다. 다운로드가 막히면 ‘송장 선택 2건 필요’처럼 남은 조작을 구체적으로 표시한다.
- 보관된 엑셀 다시 받기와 현재 매칭으로 새 엑셀 만들기를 구분한다. 기존 메시지의 파일은 당시 결과로 유지한다.
- 오래된 버튼, 중복 요청, 다른 직원이 먼저 변경한 작업은 최신 상태를 다시 확인하게 한다. 선택 권한은 기존 서버·채널·직원 허용 범위를 따른다.

## 4 현재 운영 작업의 복구 계획

1. 백업 API로 운영 DB의 일관된 복사본을 받고, 오늘의 최초·정정 업로드 원본과 작업 내역을 격리 환경에서 확인한다. 실행 중인 운영 SQLite를 검증 프로세스에서 직접 열지 않는다.
2. 최초 생성 엑셀의 번호, 재출력 파일의 번호, 현재 대표 번호를 출고별로 대조한다. 보고된 18개 상품주문과 실제 출고 수를 확인한다.
3. 수취 정보가 실제로 다른지, 과거 정보 복원 실패로 생긴 충돌인지 분리한다. 복원할 수 없는 정보는 ‘정보 미확인’으로 남긴다.
4. 직원이 정정한 최종 파일과 교체 범위를 확인한 뒤, 수정된 공통 API로 새 처리 내역을 만든다. DB 직접 수정으로 경고만 지우지 않는다.
5. 새 엑셀의 모든 상품주문번호와 송장번호를 정정 파일에 대조한다. 최초 생성 파일과 과거 내역은 그대로 보존한다.
6. 이미 네이버에 업로드한 주문이 있는지도 확인한다. 등록된 번호가 다르면 별도 정정 대상으로 분리하며, 이번 작업에서 네이버 송장을 자동 등록하거나 변경하지 않는다.

## 5 송장 구현 범위와 DB 처리

| 대상 | 변경할 내용 |
| --- | --- |
| `lib/invoices.mjs` | 과거 업로드 원본을 포함한 수취 정보 복원, 정보 누락과 실제 충돌 구분, 명시 교체와 대표 번호 선택, 파일 생성 차단 조건, 과거 파일 보존을 처리한다. |
| `server.mjs` | 공통 API에서 교체 대상·선택 번호·현재 작업 버전을 검증한다. 실제 등록 충돌을 우회하는 요청은 거부한다. |
| `lib/discord-bot.mjs`, `scripts/discord-bot.mjs` | 일괄 교체 확인, 소수 주문의 후보 선택, 새 파일 생성과 보관 파일 다운로드를 연결한다. |
| `lib/discord-workflow.mjs` | 선택 중인 작업을 이어가고 중복 요청과 오래된 선택을 검증한다. 필요한 범위만 수정한다. |
| `public/invoices.js` 및 필요한 화면 요소 | 공통 선택 결과를 표시하고, 다운로드 차단 사유와 필요한 조작을 구분한다. |
| 채팅 업무 지침과 LLM 연결 | 기능별 절차를 프롬프트에 반영하고, 실제 작업 상태를 읽어 진행 전 설명과 예외 안내를 제공한다. 의도 분류만 하는 현재 연결을 필요한 범위에서 확장한다. |

송장 수정은 기존 JSON 필드와 검토 이력 활용을 우선하므로 새 테이블·컬럼 추가를 전제로 하지 않는다. 교체 대상, 이전·새 번호, 직원, 시각, 근거를 저장한다. 기존 데이터의 호환성은 격리 복사본에서 검증한다.

스키마 변경이 없어도 선택·교체 결과를 저장하므로 운영 DB의 업무 데이터는 갱신된다. 운영 DB를 로컬 DB로 덮어쓰거나 과거 행을 일괄 삭제하지 않는다. 과거 수취 정보 복원 시 개인정보가 기존 공개 응답에 불필요하게 추가되지 않도록 한다.

### 5.1 채팅 LLM에 업무 절차를 전달하는 방식

현재 LLM은 요청을 `create_invoice`, `download_file` 등으로 분류하고 날짜를 반환한다. 작업의 전후 관계와 현재 예외 상태를 받아 안내하는 구조는 아니다. 절차를 프롬프트에 넣는 작업과 함께, 실행 전 설명·진행 상태·예외 대응을 연결해야 한다.

기능을 채팅에 추가하거나 변경할 때 아래 내용을 업무 지침에 함께 반영한다. 지침은 `prompts/discord-workflows.md` 같은 한 곳에 관리하고 실제 프롬프트에서 읽는다. 기능별 완료 조건에 지침 갱신과 검증을 포함한다.

| 지침 항목 | 포함할 내용 |
| --- | --- |
| 목적과 현재 지원 범위 | 직원이 무엇을 요청할 수 있고, 어떤 업무는 웹에서 처리해야 하는지 설명한다. 설계 중인 기능과 실제 배포된 기능을 구분한다. |
| 필요한 입력 | 파일 종류, 작업 날짜와 대상, 암호 등 필수 입력과 부족할 때 물을 내용을 정한다. 비밀값은 답변에 노출하지 않는다. |
| 정상 처리 순서 | 요청 이해, 대상 확인, 진행 전 설명, 공통 API 실행, 결과 확인, 파일 전달 순서를 적는다. |
| 직원의 판단이 필요한 지점 | 복수 송장, 일괄 교체 범위, 실제 분할 배송, 보류 등 선택과 확인이 필요한 조건을 정한다. |
| 예외와 다음 조작 | 누락·수취 정보 충돌·등록 충돌·정보 미확인·파일 오류별로 무엇이 막혔고 직원이 무엇을 해야 하는지 정한다. |
| 완료를 판단하는 근거 | 파일 생성, 네이버 등록 확인, 실물 출고 상태를 구분하고 실제 API 결과로 확인한 사실만 안내한다. |

공통 지침에는 상품명 정리, SKU 표시, 출고보드, 송장 매칭과 등록 상태 조회의 관계를 설명한다. SKU처럼 아직 구현하지 않은 기능은 배포 전까지 사용할 수 있다고 안내하지 않는다. 이번 범위 밖의 네이버 송장 자동 등록이나 취소도 실행 가능한 업무로 설명하지 않는다.

매 요청에는 필요한 현재 상태를 구조화해 전달한다. 작업 번호와 버전, 입력 파일의 역할, 대상·선택 필요·보류 건수, 오류 코드, 허용된 다음 조작을 우선 사용한다. 절차 설명만을 위해 전체 고객 정보나 엑셀 내용을 LLM에 보내지 않는다.

일반적인 매칭 요청에서는 ‘네이버 파일의 발송 대상을 기준으로 송장을 연결하고, 여러 번호가 있으면 선택을 요청하겠습니다’처럼 먼저 안내하고 진행한다. 단계별로 불필요한 승인을 추가하지 않으며, 실제 번호 선택과 일괄 교체처럼 직원의 판단이 필요한 때 확인을 받는다.

예외 안내는 API가 반환한 상태와 허용된 조작을 따른다. 예를 들어 ‘2개 출고의 송장을 골라야 엑셀을 만들 수 있습니다’라고 안내하고 실제 선택 메뉴를 제공한다. API가 실패했는데 성공했다고 말하거나, 등록 상태를 조회하지 않고 네이버 등록 완료라고 말하지 않는다.

송장 선택·교체·충돌 차단과 엑셀 생성 조건은 백엔드에서도 계속 검증한다. LLM이 절차를 잘못 해석하거나 프롬프트가 바뀌더라도 검증되지 않은 번호로 파일을 만들 수 없어야 한다. 버튼 선택과 요청 문장은 같은 공통 API로 이어진다.

## 6 SKU 적용 방침

### 6.1 상품명 정리 화면

- 정리된 제품명과 선택 옵션을 회사 바코드표에 연결한다. 매칭된 항목은 바코드를 표시하고, 미매칭 항목은 **바코드 없음**으로 표시한다. 미매칭 주문도 화면에 남긴다.
- 상품명과 옵션을 함께 판단하는 기존 정리 흐름을 유지한다. 같은 상품으로 확인되지 않은 품목이나 구성품이 불명확한 세트를 임의의 바코드에 연결하지 않는다.
- `[coupang]` 등 판매처 말머리는 SKU 연결에서 무시한다. 원본 주문과 직원이 확정한 제품명은 보존한다.
- 정상과 리퍼는 바코드표의 별도 코드를 적용한다. 맞교환은 같은 제품 바코드를 사용하더라도 출고 유형을 별도로 보존한다.
- 직원이 제품명을 수정하면 바코드 연결도 다시 확인한다. 이전 상품의 바코드가 그대로 남지 않도록 한다.

### 6.2 출고보드 집계와 제품 제목

- 매칭된 항목은 **바코드와 출고 유형**을 기준으로 묶는다. 이전 합의에 따라 맞교환은 일반 출고와 따로 표시한다. 리퍼는 별도 바코드로 구분한다.
- 같은 바코드가 확인되면 이름이나 판매처 말머리가 달라도 수량을 합친다. 예를 들어 일반 6묶음과 `[coupang]` 1묶음은 7묶음으로 표시한다.
- 그룹 제목은 현재 조회 범위에서 가장 많이 쓰인 정리된 제품명을 사용한다. 집계 대상의 중복을 제거한 뒤 명칭별 출현 수를 세고, 동률이면 이름 오름차순으로 고정한다. 이 규칙은 제목에만 적용하며 수량 집계 방식은 바꾸지 않는다.
- 바코드가 없는 서로 다른 제품을 하나로 합치지 않는다. 기존 제품명 구분을 유지하고 ‘바코드 없음’을 표시한다.
- 확인한 주문 보드의 ‘묶음’과 신규 주문현황의 ‘개’ 등 기존 수량 단위와 중복 제거 기준을 보존한다. 같은 바코드라는 이유로 주문 원본이나 출고 레코드를 합치지 않는다.

### 6.3 SKU 데이터와 변경 대상

현재 코드에는 SKU 마스터와 제품명 연결 기능이 없다. 기준 자료는 `skuid_babestellar.xls`이며, 확정된 마스터를 운영에서도 읽을 수 있는 형태로 저장하고 배포해야 한다. 개발용 참고 폴더나 일회성 분석 파일을 운영 의존성으로 사용하지 않는다.

상품 마스터와 주문행별 바코드 저장 구조를 추가한다. 바코드는 문자열로 저장한다. 기존 DB 필드를 먼저 확인하고 필요한 컬럼·마스터 저장 구조만 추가하며, 반복 실행해도 안전한 마이그레이션과 백업 복구를 검증한다. **송장 수정과 달리 SKU 단계는 DB 구조 변경이 예상된다.**

기존 주문에도 같은 연결 기준을 적용하되 확실하게 매칭되는 바코드만 채운다. 과거 정리명·원본 행·수량·생성 엑셀은 변경하지 않는다. 마스터에 없는 품목의 새 바코드 발급은 이번 구현에 포함하지 않는다.

변경 대상은 `lib/naming.mjs`, `lib/database.mjs`, 상품명 정리 화면과 API, `lib/shipping.mjs`, `lib/shipping-preview.mjs`, `public/shipping-board.js` 및 관련 테스트다. SKU 마스터 연결은 두 보드에서 공통으로 사용한다.

송장 핵심 검증은 오늘 원본과 운영 백업의 격리 복사본, 가상 분할 배송·실제 충돌 사례를 함께 사용한다. SKU는 기존 커버리지 조사 결과와 실제 주문명 변형을 사용한다. 위 표는 실행할 테스트 목록이며 아직 통과한 결과를 의미하지 않는다.

LLM 안내는 정확히 같은 문장을 반환하는지보다 필요한 사실과 선택을 알맞게 전달하는지 검증한다. 모의 LLM 응답을 이용한 공통 API·업무 흐름 테스트와, 가상 요청을 실제 모델에 보내는 업무 지침 평가를 구분한다. 기능 변경 시 프롬프트 버전과 대표 요청 사례도 함께 갱신한다.

파일 매칭과 SKU 집계 검증에는 실제 네이버 API가 필요하지 않다. 등록 상태와 다른 송장 등록 충돌은 모의 응답으로 검증하고, 운영 복구에 필요한 경우에만 해당 주문을 조회 전용 API로 확인한다. 네이버 송장 등록·변경 호출은 이번 범위에 포함하지 않는다.

## 8 구현과 배포 순서

1. **현재 충돌 재현과 원인 확정** — 운영 백업과 업로드 원본으로 오늘 문제를 재현하고 실제 충돌과 오탐을 분리한다.
2. **송장 공통 처리 수정** — 원본 복원, 명시 교체, 소수 후보 선택, 파일 보존을 API와 로컬 테스트에서 검증한다.
3. **웹과 디스코드 연결** — 일괄 정정 한 번 확인과 예외 주문만 선택하는 흐름, LLM의 진행 전 설명과 예외 안내를 가상 업무로 확인한다. 배포되는 기능과 업무 지침을 함께 갱신한다.
4. **송장 수정 배포와 현재 작업 복구** — 검증 결과와 실제 변경 파일을 확인한 뒤 배포한다. 오늘 작업은 확정된 정정 원본으로 새 내역을 만들고 엑셀을 대조한다.
5. **SKU 구현과 별도 배포** — 승인된 마스터, DB 변경, 화면 표시, 보드 집계 순서로 검증한다. 송장 수정과 별도 커밋·배포 단위로 나눈다.

각 배포 전 백업 API로 DB를 보관하고 현재 코드와 설정을 확보한다. 새 소스와 필요한 마스터·마이그레이션만 반영하며 운영 DB와 API 키는 덮어쓰지 않는다. 배포 후 웹·봇의 같은 결과, 기존 파일 보존, 서비스 상태를 확인한다.

문제가 생기면 이전 코드로 복구하되 배포 뒤 발생한 실제 업무 데이터를 통째로 과거 DB로 되돌리지 않는다. 특히 SKU DB 변경은 이전 코드와의 호환성을 먼저 확인한다. 구현 완료 보고에는 실행한 검증과 남은 제한사항, DB 변경과 운영 반영 여부를 구분해 적는다.

## 9 완료 기준

- 오늘 같은 사고는 직원의 일괄 확인 한 번으로 정정하고, 1~2개 예외는 해당 주문만 선택할 수 있다.
- 거짓 수취 정보 충돌은 없어지고 실제 위험한 충돌은 계속 차단된다. 다운로드 차단 시 필요한 조작이 표시된다.
- 직원이 확정한 송장이 웹·디스코드·새 엑셀에서 일치하고 과거 이력은 보존된다.
- 채팅 LLM이 지원 중인 업무의 절차를 알고, 진행 전 설명과 실제 상태에 맞는 예외 안내를 제공한다. 기능·프롬프트·검증 사례가 함께 갱신된다.
- 상품명 정리 화면에서 바코드 또는 ‘바코드 없음’을 확인할 수 있다.
- 출고보드는 같은 바코드끼리 정확한 수량으로 묶고 최빈 제품명을 제목으로 사용한다. 리퍼·맞교환·미매칭 제품 구분은 유지된다.

- 운영 백업 복사본의 작업 19에서 거짓 충돌 17개를 해소하고 18개 상품주문 모두 재출력 번호로 엑셀을 생성했다. 기존 생성 파일 18개의 해시와 DB 무결성을 확인했다. 이 검증은 격리 복사본에만 적용했다.
- 채팅 첨부부터 개별 선택, 분할 대표, 일괄 교체와 실제 엑셀 생성까지 공통 HTTP API로 검증했다. 저장된 분할 대표는 웹·채팅에서 다시 선택할 수 있다.
- 가상 주문으로 실제 웹 화면의 선택·저장·다운로드를 확인했다. 디스코드의 실제 직원 채널에 시험 메시지를 게시하거나 운영 봇을 교체하지 않았다.
- 새 업무 지침을 실제 LLM 입력에 연결하고, `gpt-6.1-sol`에 고객 정보 없는 가상 요청 4개를 보내 일반 생성·교체·선택 필요·미지원 등록 요청의 안내를 확인했다.
- 전체 자동 테스트는 311개 통과했고 실패·건너뜀은 없었다. 확인 로그와 운영 복사본 재현 결과는 `.work/invoice-chat-20261114/`에 보관했다.
- 송장 수정에 따른 새 DB 컬럼·테이블은 추가하지 않았다. 선택·교체 근거는 기존 업무 JSON과 검토 이력에 저장한다.

송장 충돌, 웹·채팅 교체·선택과 LLM 업무 지침은 `20d426e`로 커밋했다. 운영 배포와 실제 운영 작업의 정정은 진행하지 않았다.

## 11 11월 14일 SKU 구현 결과

- 회사 원본의 35개 바코드를 `data/sku-catalog.json`에 보존했다. 확인된 제품명 별칭 80개로 22개 코드를 연결하며, 미확인 품목·세트는 ‘바코드 없음’으로 남긴다.
- 상품명 의미와 옵션은 기존 LLM이 정리한다. SKU는 정리 결과의 검증된 별칭으로 연결하고, 정리명이 포함된 파일 가져오기·기존 이름 재사용·직원 수정·신규 주문 미리보기에도 같은 기준을 적용한다.
- `rows.sku_barcode` 문자열 컬럼을 추가하고 기존 활성 주문을 갱신한다. 로컬 API 백업 전후 14개 테이블의 기존 값·원본·생성 파일을 비교해 SKU 외 변경이 없음을 확인했다. 반복 실행과 DB 무결성도 확인했다.
- 상품명 화면의 바코드·미매칭 표시와 두 출고보드의 바코드·출고 유형별 집계를 구현했다. 정상·리퍼·맞교환과 서로 다른 미매칭 제품은 분리한다.
- 실제 11월 13일 오전 작업은 총 20묶음을 유지하며 9개 제품 그룹에서 8개로 줄었다. 완전밀착 새싹 D타입 High(13cm)의 일반 6묶음과 쿠팡 1묶음이 바코드 `8809538930160`의 7묶음으로 표시된다.
- 실패를 먼저 확인한 SKU 회귀 테스트를 추가했고 전체 327개가 통과했다. 로컬 실제 화면도 확인했다. 결과는 `.work/sku-20261114/`에 보관했다.
- SKU는 로컬 서버에 반영했다. 운영 DB·네이버 API·운영 봇은 변경하지 않았으며, SKU 커밋·푸시·배포는 별도 진행 대상으로 남긴다.

## 12 상품·바코드 관리

- 바코드를 SKU로 유지하고 `/products.html`에서 새 상품 등록과 미연결 제품명의 기존 SKU 연결을 구현했다. 입력 형식·중복·다른 SKU로의 재연결을 검사한다. 텍스트 일괄 업로드는 이번 범위에 넣지 않았다.
- 초기 마스터는 DB의 `sku_products`·`sku_aliases`로 옮기며 이후 등록 내용은 DB 백업에 포함된다. 연결은 기존 활성 주문과 이후 주문에 적용하고 제품명·원본·수량·기존 엑셀은 보존한다.
- 전체 테스트 330개와 가상 실제 화면의 오류·등록·연결을 확인했다. 로컬 적용 전후 기존 14개 테이블의 값과 파일이 동일하며 새 관리 테이블 두 개만 추가됐다. 운영 배포는 진행하지 않았다.

## 13 공통 메뉴와 AI 호출 비용

- 다섯 업무 화면에 같은 메뉴·현재 위치 표시를 적용하고 화면별 날짜·새 작업 조작을 업무 영역으로 분리했다. 넓은 화면과 좁은 화면의 이동·표시를 확인했다.
- AI 호출 내역에 호출별 토큰·추정 비용(USD), 날짜·목적별 비용·평균을 표시한다. 캐시 읽기·쓰기와 출력을 구분하고 미산정 호출을 0원으로 취급하지 않는다. 새 호출은 당시 단가와 계산을 `llm_calls.cost_json`에 보존한다.
- 과거 호출은 현재 공식 Standard·기본 캐시 단가를 가정한 계산이며 세금·계약 할인은 제외한다. 로컬 동기화본 64회의 합계 $0.5342822를 독립 SQL 계산으로 대조했다. 기존 기록은 수정하지 않았다.
- 최종 자동 테스트는 336개 통과했다. 배포는 소스와 초기 마스터만 반영하며 운영 DB·환경 설정·원본 파일·기존 생성 엑셀은 보존한다.

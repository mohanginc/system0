# 주문 상품명 정리 기능

여러 주문 엑셀을 한 작업으로 저장하고, 실제 선택 옵션을 반영한 상품명을 AI로 정리합니다. 직원은 화면에서 정리된 제품명과 검수 메모를 수정·저장하고 송장용 주문 파일을 다운로드합니다.

## 기본 사용

1. `.xls`·`.xlsx` 파일을 선택하거나 끌어 놓고 **선택한 파일 불러오기**를 누릅니다.
2. **미정리 상품명 정리**를 누릅니다. 체크한 항목만 정리할 수도 있습니다. 기존 이름을 먼저 재사용하고, 새 AI 판단이 필요한 항목만 OpenAI API를 호출해 비용이 발생합니다.
3. **정리된 제품명**과 **검수 메모**를 수정합니다. **검수 완료**를 체크·해제하거나 **선택 항목 검수 완료**를 누르면 해당 항목의 이름·메모·검수 상태를 즉시 저장합니다.
4. 나머지 미저장 수정이나 삭제 예정 항목은 **수정 내용 저장**으로 따로 저장합니다. 저장 전까지 화면에 미저장 수정 건수와 **삭제 예정 주문 N행**을 표시합니다.
5. **주문 파일 · 상품명 교체** 또는 **검수용 상품명 목록**을 선택하고 **엑셀 다운로드**를 누릅니다.

검수 완료 저장은 같은 상품명 항목에 연결된 원본 주문의 모든 행에 반영합니다. 다른 항목의 미저장 수정과 삭제 예정은 유지합니다. 실패하면 입력값과 선택을 유지하며, 검수 상태는 저장에 성공했을 때만 반영합니다.

상품명이 비어 있는 항목은 정리하거나 직접 입력해야 다운로드할 수 있습니다. 검수 전 상품명도 다운로드할 수 있으며 화면에서 미검수 건수를 확인할 수 있습니다. 저장하지 않은 수정이나 삭제 예정 항목이 있으면 AI 정리와 다운로드 전에 저장해야 합니다. 저장에 실패하면 입력한 내용과 삭제 예정 선택을 유지하므로 오류를 확인한 뒤 다시 저장할 수 있습니다.

## 작업 선택과 검수

인트로는 한국 시간 기준으로 같은 브라우저에서 하루 첫 방문에 한 번 표시합니다. 당일 새로고침이나 재실행에는 다시 표시하지 않습니다. 브라우저 데이터를 지우거나 다른 브라우저를 사용하면 다시 표시될 수 있습니다.

**새 작업**은 파일 선택·상품명 화면·검색 조건을 초기화합니다. 기존 작업은 보관되며, 새 파일을 불러올 때 별도 작업으로 저장됩니다. 수정 내용이나 삭제 예정 항목이 있으면 먼저 저장한 뒤 새 작업을 시작하거나 다른 날짜를 선택합니다. 다른 작업을 열거나 페이지를 닫을 때도 미저장 수정·삭제 내용이 있으면 경고합니다.

**지난 작업**에서 날짜를 고르면 그날의 작업을 조회합니다. **모든 작업 보기**는 작업 제목과 남은 주문 행 수를 보여주며, 처음에는 내용을 접어 둡니다. 작업 제목을 누르면 해당 작업의 상품명을 펼치거나 접을 수 있습니다. 제목 옆 **작업 열기**나 작업 선택 목록에서 개별 작업을 열어 정리·검수·다운로드를 이어갑니다. 작업 날짜와 시간은 한국 시간을 기준으로 합니다.

상품명 화면은 원본·옵션·정리된 이름·검수 상태·메모가 같은 주문 행을 한 항목으로 묶습니다. 항목에 표시된 **주문 N행**이 해당 항목에 연결된 실제 주문 행 수입니다. 항목을 수정·저장하면 연결된 모든 행에 반영됩니다. 중복 주문 행 자체는 보존합니다.

검색은 원본·옵션·정리된 상품명·메모를 함께 찾습니다. 상태 필터와 체크박스로 처리 대상을 정할 수 있으며, 표 머리의 체크박스는 현재 표시된 항목을 선택합니다. 항목은 80개씩 표시하고 **더 보기**로 추가 표시합니다.

| 검수 상태 | 의미 |
| --- | --- |
| 미정리 | 정리된 제품명이 비어 있음 |
| 검수 대기 | AI 결과 또는 직접 입력한 이름을 직원이 확인하기 전 |
| 확인 필요 | AI가 정보 부족이나 충돌을 발견했으며 메모 확인이 필요함 |
| 검수 완료 | 직원이 상품명을 확인함 |

## 파일 처리와 AI 판단

상품명 컬럼은 `원상품명`, `제품명 원본`, `상품명` 중 하나여야 합니다. 첫 20행에서 헤더를 찾으며, 상품명 컬럼이 없는 보조 시트는 처리 대상에서 제외하고 다운로드 원본에 보존합니다. 기존 헤더 없는 `제품명_옵션명_연결.xlsx`도 읽습니다. 이 파일의 B열 직원 명칭과 C열 메모는 보존합니다.

빈 상품명 등 오류가 있으면 파일·시트·행 위치를 알리고 전체 가져오기를 취소합니다. 한 번에 최대 100개, 파일당 10MB, 합계 50MB까지 불러올 수 있습니다. 원본 파일·주문 행·출처는 SQLite에 함께 저장합니다.

**미정리 상품명 정리**는 삭제되지 않은 지난 작업·주문 행에서 원본 상품명과 옵션이 정확히 같고 현재 지침으로 정리된 저장 이름을 먼저 찾습니다. 같은 지침의 결과 중 가장 최근의 직원 검수 완료 이름을 우선하고, 없으면 기존 AI 초안의 이름·검수 상태·메모를 이어 씁니다. 옵션이 다르면 재사용하지 않습니다. 현재 작업에서 이미 정리하거나 수정한 이름은 바꾸지 않습니다.

이름에는 적용한 지침의 버전(`namingVersion`)을 함께 저장합니다. 지침이 바뀌거나 버전이 없는 이전 자료만 있으면, 그 상품의 다음 주문을 LLM으로 한 번 다시 정리합니다. 이전 이름과 검수 메모는 참고 정보로 전달하며, 성공한 새 결과는 다음 주문부터 재사용합니다. 실패하거나 응답이 잘못되면 갱신 완료로 기록하지 않습니다. 과거 작업의 이름과 검수 이력은 그대로 보존합니다. 미정리 항목에 직원이 직접 입력한 새 이름도 현재 지침의 버전으로 저장하며, 검수 완료 후 재사용할 수 있습니다.

재사용할 이름이 없으면 AI가 [상품명 판단 지침](../prompts/product-names.md)에 따라 원본 상품명과 선택 옵션을 함께 읽습니다. 상품명과 옵션의 속성이 충돌하면 실제 선택 옵션을 반영합니다. 의미 판단을 규칙으로 대신하지 않습니다. 같은 원본과 옵션에 대한 새 호출은 한 작업 안에서 묶습니다.

이름 순서는 **이름 디자인(소재) 속통타입 사이즈명(실사이즈) 리퍼**입니다. 완전밀착 수유쿠션 본품의 속통타입은 **D타입**, 양손프리는 **3룸솜속통·쿠션펌·하드 쿠션** 중 실제 제품의 타입을 표기합니다. 속통 선택이 없으면 원제목을 참고하고, 불확실하면 확인 필요로 표시합니다. 커버·속통 단품에는 본품의 속통 표기를 임의로 붙이지 않습니다.

정리된 제품명 아래에는 처음 이름을 얻은 경로를 **AI로 정리**, **기존 이름 재사용**, **직접 입력**, **기존 자료**로 표시합니다. API의 주문 행 `nameSource`는 각각 `ai`·`reused`·`manual`·`imported`이며, 미정리 항목은 빈값입니다.

최초 AI 결과, 직원이 저장한 명칭·메모·검수 상태와 수정 이력을 보존합니다. AI 호출이 중간에 실패해도 이미 저장한 결과는 유지합니다. 다시 정리하면 남은 미정리 항목만 처리하며, 잘못된 AI 응답 묶음은 저장하지 않습니다. AI 정리 중에는 수정·삭제·다운로드를 잠급니다.

## AI 호출 내역

화면 아래 **AI 호출 내역**을 누르면 별도 페이지 `/llm-usage.html`에서 날짜 범위와 목적을 골라 조회합니다. 한국 시간 기준 날짜·목적별 호출 횟수와 성공·실패·진행 중 횟수, 조회 범위 합계를 보여줍니다.

상품명 정리는 고유 상품명·옵션을 최대 20개씩 묶어 한 번 호출합니다. 주문 행 수나 상품명 개수와 호출 횟수는 다르며, 실패한 호출과 재시도도 각각 집계합니다. 기존 이름 재사용은 호출 횟수를 늘리지 않습니다. 기록 시작 시점 이전의 과거 호출 횟수는 복원할 수 없습니다.

목적은 SQLite `llm_purposes`의 `code`·`name`·`active`로 관리하며, 기본 목적은 `product_names` / **상품명 정리**입니다. 새 목적은 DB에 `code`·`name`·`active=1`을 INSERT하고 해당 기능에서 공통 `callLlm` 함수에 `purposeCode`를 전달합니다.

## 출고 보드

화면 위 **출고 보드 ↗**를 누르면 읽기 전용 화면 `/shipping-board.html`이 열립니다. **확인한 주문**과 **신규 주문현황** 두 모드를 제공합니다. 상품명 항목을 누르면 **수취인·전화번호·동네**가 펼쳐지며, 신규 주문현황에는 **수량**과 상품명 확인 필요 사유도 표시합니다. 동네는 원본에 명시된 시·도/시·군·구·읍·면·동까지만 표시하며 전체 주소를 노출하지 않습니다. **전체 화면**으로 확대하고 **전체 화면 종료**로 돌아올 수 있습니다.

**확인한 주문**은 엑셀을 불러와 저장한 작업을 조회합니다. 한국 시간 기준 작업 등록일을 달력에서 고른 뒤 **모든 작업 모아 보기** 또는 개별 작업을 선택합니다. 정리된 상품명별 **출고 묶음 수**는 원본 주문 1행을 1묶음으로 셉니다. 실제 제품 개수나 원본 수량 컬럼의 값과는 다릅니다. 처음 열 때와 날짜·작업 선택, **새로고침** 때 조회합니다.

확인한 주문은 삭제되지 않은 작업·행만 조회합니다. 선택한 날짜·작업 범위에서 같은 출고번호는 한 번만 세며, 서로 다른 정리된 이름이나 수취인 정보가 있으면 **중복 충돌 · 확인 필요**로 따로 표시합니다. 이름이 없는 묶음은 **미정리**로 표시합니다. 출고번호가 없는 행은 원본 행별로 집계하며 재업로드 중복 여부는 확인할 수 없습니다. 현재 **송장 정보 연결 전**으로 표시하며 검수 완료·파일 다운로드·화면 색상을 송장 발행이나 출고 완료로 판단하지 않습니다.

**신규 주문현황**은 포장 담당자가 사전 포장을 준비하는 조회 화면입니다. **갱신**을 누르면 결제 시각 기준 최근 7일의 결제 완료(`PAYED`)·발주 미확인(`NOT_YET`) 주문을 24시간씩 나누어 마지막 페이지까지 조회하고 상품명을 정리합니다. 조회 기간과 마지막 성공 시각은 한국 시간으로 표시합니다. 네이버 주문은 조건형 GET으로만 조회하며 발주확인·발송·취소를 호출하지 않습니다.

신규 주문의 **잔여 주문 수량**은 부분 취소를 반영한 `remainQuantity`의 합입니다. 상품주문번호를 문자열로 보존하고 상품주문별 행을 유지하며, 합배송이나 상자 수를 추정하지 않습니다. 갱신 성공 시 전체 결과를 교체하고 0건이면 비웁니다. 실패하면 마지막 성공 결과를 유지합니다. 두 모드 모두 주기적 자동 갱신은 없으며 신규 조회·정리 중에는 중복 갱신을 차단합니다.

신규 상품명은 기존과 같은 [판단 지침](../prompts/product-names.md)과 LLM을 사용하며 고객 정보는 LLM에 보내지 않습니다. 원본 상품명·옵션이 정확히 같고 현재 지침으로 정리된 저장 이름은 읽어서 재사용합니다. 조회 주문·작업·임시 상품명은 DB나 파일에 저장하지 않고 현재 화면 메모리에만 유지하므로 다시 열면 재조회해야 합니다. 임시 결과를 다음 조회에 영구 재사용하지 않아 갱신할 때 AI 비용이 다시 발생할 수 있습니다. 호출 통계만 목적 `product_names_preview`(**신규 주문현황 상품명 정리**), `batchId: null`로 저장하며 **AI 호출 내역**에서 확인합니다.

네이버 설정은 `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET`을 사용합니다. 기존 환경 변수와 `.env`의 OpenAI 설정은 유지하며, 네이버 값이 없으면 `SYSTEM0_ENV_FILE` 또는 기본 `%LOCALAPPDATA%/system0/.env`에서 읽습니다. 설정을 바꾼 뒤 서버를 다시 시작합니다.

## 삭제와 데이터 보존

작업과 주문 행은 DB의 `is_deleted` 플래그로 삭제 표시합니다. 원본 파일·원본 상품명·AI 결과·저장된 직원 검수 내용·수정 이력은 DB와 백업에 보존합니다. DB에 삭제 표시한 내용은 일반 화면·API 조회·AI 정리·직원 수정·다운로드 대상에서 제외합니다.

**작업 삭제**는 모든 작업 보기의 제목 옆과 개별 작업 화면에 있습니다. 미저장 수정이나 삭제 예정 항목이 있어도 누를 수 있습니다. 확인 창에서 미저장 변경을 취소한다는 안내와 남은 주문 행 수를 확인하면 작업에 즉시 삭제 플래그를 적용합니다. 연결된 주문 행과 저장된 검수 기록은 그대로 보존합니다.

개별 작업에서 **항목 삭제**로 한 상품명 항목을 삭제 대상으로 고르거나, 체크박스로 선택한 뒤 **선택 항목 삭제**를 누릅니다. 확인 창에 상품명 항목 수와 연결된 실제 주문 행 수를 표시합니다. 확인하면 해당 항목을 화면에서 제외하고 **현재 주문 행**과 검수 집계를 미리 갱신합니다.

삭제 대상으로 고른 항목 자체의 미저장 수정은 버리며, 다른 항목의 입력 내용과 선택은 유지합니다. **수정 내용 저장**을 누르면 다른 항목의 수정과 주문 행 삭제를 함께 DB에 반영합니다. 예를 들어 **주문 3행**으로 묶인 항목 하나를 삭제 대상으로 고르고 저장하면 주문 3행 모두 조회·처리·다운로드에서 제외됩니다. 저장 전에는 DB에 삭제 플래그를 적용하지 않으며, 저장하지 않고 이동하면 삭제 예정 선택도 취소됩니다.

저장 후 날짜별 작업 목록도 남은 행 수로 갱신합니다. 모든 행을 삭제해도 작업은 0행으로 남으며 다운로드할 수 없습니다. AI 정리 중에는 작업 삭제와 항목 삭제를 할 수 없습니다.

삭제한 작업이나 행을 복원하거나 DB에서 완전히 지우는 관리 화면은 이후 요청 시 구현합니다.

## 다운로드

**주문 파일 · 상품명 교체**는 남은 주문 행의 상품명 셀을 정리된 제품명으로 바꾼 `.xlsx`를 만듭니다. 삭제한 주문 행은 파일에서 제거하며, 원본 시트·헤더·컬럼 순서와 남은 주문 행 순서·상품명 외 값은 보존합니다. 검수 상태 등의 컬럼은 추가하지 않으며, 남은 중복 행과 빈 행도 유지합니다. 글꼴·색상·테두리 등 장식 서식은 보존하지 않습니다. Microsoft Excel 설치나 실행은 필요하지 않습니다.

여러 원본 파일은 파일별 XLSX 결과를 ZIP으로 묶고, 주문 행이 모두 삭제된 파일은 제외합니다. 처음에 여러 파일을 불러온 작업은 결과 파일이 하나만 남아도 ZIP으로 다운로드합니다.

다운로드할 원본 파일에서 일부 행을 삭제했고 상수 산술식 이외의 수식, 배열 수식, 자동필터 범위를 제외한 이름 정의, 내부 링크가 있으면 참조가 달라지는 것을 막기 위해 주문 파일 다운로드를 중단합니다. 이 경우 검수용 상품명 목록을 다운로드하거나, 원본에서 해당 참조를 제거한 파일을 다시 불러옵니다. `3*3800`처럼 숫자와 산술 연산자만 사용하는 수식과 행 삭제가 없는 파일의 수식은 보존합니다.

**검수용 상품명 목록**은 제품명 원본·정리된 제품명·옵션명·검수 상태·검수 메모를 내보냅니다. 같은 원본·옵션·정리된 이름·검수 상태·메모는 한 행으로 묶습니다.

원본 파일이 저장되지 않은 이전 작업은 주문 파일 다운로드가 제한됩니다. 원본을 다시 불러오거나 검수용 상품명 목록을 다운로드합니다.

## 업무 API

API는 로컬 주소에서 호출하며, 오류는 `{ "error": "안내 문구" }`로 응답합니다. 화면도 아래 API를 사용합니다. 현재 채팅 연결은 제공하지 않습니다.

| 메서드와 경로 | 요청과 결과 |
| --- | --- |
| `GET /api/status` | 앱·모델·API 키 설정 여부 확인 |
| `GET /api/llm/purposes` | 목적 목록 `purposes`와 기록 시작 시점 `trackingStartedAt` |
| `GET /api/llm/usage` | `from`·`to`·`purpose`로 조회. 일별·목적별 `days`, 합계 `totals`, `trackingStartedAt` |
| `GET /api/shipping/dates?month=YYYY-MM` | 확인한 주문의 월간 작업 등록일 조회. 월 생략 시 한국 시간 이번 달. `{ month, days: [{ date, batchCount, invoiceState }] }` 응답 |
| `GET /api/shipping/board?date=YYYY-MM-DD&batchId=...` | 확인한 주문 조회. 날짜 생략 시 한국 시간 오늘, `batchId` 생략 시 그날 모든 작업. `date`·`batches`·`selectedBatchId`·`groups`·`summary`·`issues`·`invoiceState` 응답. 그룹의 `needsAttention`은 중복 충돌 표시, `shipments` 상세는 `id`·`recipient`·`phone`·`neighborhood` 제공 |
| `POST /api/shipping/preview` | 본문 없이 신규 주문 조회·상품명 정리. `mode: "new"`·`from`·`to`·`updatedAt`·`invoiceState`·`summary`·`groups` 응답. `summary.quantity`와 그룹 `count`는 잔여 수량 합, `shipments`는 상품주문별 식별자·수취인·전화·동네·수량·확인 사유 제공. 중복 실행은 `409`, 조회·정리 실패는 `400` |
| `GET /api/batches?date=YYYY-MM-DD` | 한국 시간 기준 날짜의 작업 목록. 날짜 생략 시 전체 목록 |
| `POST /api/import` | multipart `files`로 엑셀 업로드. 새 작업 상세 응답 |
| `GET /api/batches/:id` | 작업·주문 행·이름 출처·상태별 요약·AI 진행 여부 |
| `POST /api/batches/:id/normalize` | 선택 시 `{ rowIds: [...] }`, 생략 시 전체 미정리 행. 기존 이름 재사용 후 필요한 AI 판단을 수행하고 작업 상세 응답 |
| `PATCH /api/batches/:id/rows` | `{ changes: [{ id, cleanedName, reviewNote, status }], deletedRowIds: [...] }`로 수정·검수·삭제 저장. 작업 상세 응답 |
| `DELETE /api/batches/:id` | 작업 삭제 표시. `{ deleted: true }` 응답 |
| `DELETE /api/batches/:id/rows` | `{ rowIds: [...] }`로 주문 행 즉시 삭제 표시. 남은 작업 상세 응답, 기존 API 호환 유지 |
| `GET /api/batches/:id/export?kind=orders` | 상품명 교체 주문 파일. `kind=names`는 검수용 목록 |
| `POST /api/backup` | 원본·검수 내용·이력을 포함한 일관된 SQLite 백업 다운로드 |

PATCH의 `deletedRowIds`는 생략할 수 있어 기존 수정 요청도 그대로 동작합니다. 삭제만 저장할 때는 `changes: []`와 삭제할 행 번호를 보냅니다. 수정과 삭제는 한 트랜잭션으로 반영하며, 같은 행을 수정·삭제에 동시에 넣거나 일부 변경이 잘못되면 전체 저장을 취소합니다. 화면의 항목 삭제는 이 PATCH를 사용합니다.

검수 완료 체크·해제와 선택 항목 검수 완료는 해당 항목의 주문 행을 `changes`로 보내 즉시 저장합니다. 다른 항목의 미저장 수정이나 삭제 예정은 이 요청에 포함하지 않습니다.

AI 호출 내역의 `from`·`to`는 필수이며 `YYYY-MM-DD`로 지정합니다. `purpose`는 목적 코드이며 생략하면 모든 목적을 조회합니다. 날짜·목적별 결과는 한 번에 10,000행까지 조회합니다. `days`의 각 항목은 `date`·`purposeCode`·`purposeName`·`calls`·`succeeded`·`failed`·`running`을 반환합니다. 이후 채팅 연결도 화면과 같은 업무 API를 사용합니다.

삭제된 작업의 상세·정리·수정·삭제·다운로드 요청은 `404`로 거절합니다. AI 정리 중인 작업을 변경하거나 다운로드하면 `409`로 거절합니다. 주문 행 변경에서 다른 작업의 행·이미 삭제된 행·중복 행 번호를 요청하면 `400`으로 거절하고 전체 요청을 취소합니다.

설치·실행·백업 복구 방법은 [README](../README.md)를 따릅니다. 현재 범위는 주문 상품명 정리와 출고 조회이며 주문·재고·송장 발행·출고 처리·포장 관리와 채팅 연결은 이후 사용자가 요청할 때 진행합니다.

## 송장 처리 개발 계획 (미구현)

다음 내용은 합의된 계획이며 현재 제공하는 기능과 구분합니다.

### 이번 개발 범위

- 별도 송장 처리 화면에서 ① 네이버 주문파일(여러 개 가능)과 ③ 최종 택배사 송장파일을 올립니다. 이미 저장한 ② 레거시 원본을 재사용하고 날짜·작업 구분 없이 유효 주문을 찾아 매칭합니다. 삭제된 작업·행은 자동 처리 대상에서 제외합니다.
- 식별번호로 상품주문·내부 출고·송장을 연결하고, 여러 작업에 중복된 상품주문은 한 번만 처리합니다. 번호 누락·충돌·미매칭은 원본 위치와 이유를 표시하며, 추측해 자동 확정하거나 조용히 건너뛰지 않습니다.
- 합배송은 해당 출고의 상품주문들에 같은 송장을 연결합니다. 같은 출고의 분할 상자는 차수 기준 첫 송장을 대표로 삼고, 재출력은 근거가 명확한 최신 유효 송장을 선택합니다. 출고전 취소 가능성·구분이 모호한 송장은 확인 대상으로 남깁니다. 서로 다른 네이버 주문번호의 합포장은 센터 처리 대상으로 구분합니다.
- 확정 결과로 네이버 수동 업로드용 `.xlsx`를 만듭니다. 실제 파일 업로드·스마트스토어 등록은 담당자가 수행하고 발견한 예외를 보완합니다. 기본적인 누락·중복·출력 검증은 개발 중 수행합니다. 직접 전송과 모의 전송 기능은 이번 범위에 포함하지 않습니다.
- 등록 상태 확인은 네이버 조회 API로 실제 반영 여부를 확인합니다. 파일 다운로드만으로 완료 처리하지 않으며, 필요한 등록이 모두 확인된 출고만 보드에서 회색으로 표시합니다. 미해결·실패·조회 불가 항목은 완료로 표시하지 않습니다. 발주 확인·발송 등 주문 상태 변경 API는 호출하지 않습니다.
- 송장용 파일·매칭·선택 근거·전체 송장 이력을 기존 상품명 원본과 구분해 저장합니다. 재업로드로 기존 결과를 잃거나 완료 주문을 중복 처리하지 않도록 하며, 업무 화면과 향후 채팅이 같은 업무 API를 사용할 수 있게 구성합니다.

### 향후 확장 시 지킬 기준

- **여러 몰의 주문 수집·송장 등록:** 몰·스토어·주문번호·상품주문번호를 문자열로 보존하고, 외부 주문 식별은 몰·스토어·상품주문번호 조합으로 구분합니다. 공통 매칭 결과와 몰별 가져오기·출력·API 처리를 구분하되, 다른 몰의 연동 코드나 범용 연동 프레임워크는 미리 만들지 않습니다.
- **상차 전 송장 스캔:** 실제 상자/내부 출고에 속한 송장과 차수, 재발급 전후 관계, 현재 유효 여부를 보존합니다. 나중에 system0의 최신 송장파일과 스캔 번호를 대조해 구송장·미등록 번호·중복 스캔을 경고할 수 있어야 합니다. 네이버 등록 전에도 검사할 수 있으며, 분할 상자의 모든 유효 송장을 인정합니다. 스캔 후 재발급이 발생하면 과거 기록은 보존하고 상차 상태를 다시 확인해야 합니다.
- **상태 분리:** 송장 유효 여부, 상차 확인 여부, 몰 송장 등록 여부는 서로 다른 상태입니다. 최신 송장 등록은 실물 상차를 증명하지 않으며, 몰에 등록한 대표 송장 하나가 실제 여러 상자의 송장을 대신하지 않습니다. 송장만 스캔해서 다른 주문의 유효한 스티커 오부착까지 판별할 수는 없으므로, 향후 해당 검증에는 포장 대상 주문·제품 식별도 필요합니다.

현재 단계에서는 스캐너 화면·장치 연결·상차 처리 기능을 구현하지 않습니다.
